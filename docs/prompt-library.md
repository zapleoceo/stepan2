# Библиотека промтов и независимость промта филиала

Промт филиала складывается из трёх слоёв. Раньше слоя было полтора: один Python-константа
на всех и жёсткий список слагов документов.

| Слой | Где живёт | Кто общий |
|---|---|---|
| **CRAFT** | код, `app/modules/promptlib/craft.py` | у всех филиалов один |
| **METHOD** | ДАННЫЕ филиала (`knowledge_doc`, `category='method'`), клонируется из библиотеки | свой у каждого |
| **BUSINESS** | ДАННЫЕ филиала: персона, каталог продуктов, факты, часы, валюта | свой у каждого |

CRAFT — только то, что верно везде: не выдумывать факты, один вопрос за раз, отвечать на
заданный вопрос, писать на языке лида, формат JSON и кап бабблов. Никаких процентов, номеров
тредов, «Kak», WIB и рупий: это измерения одного рынка, они уезжают в METHOD того рынка.
Тест `tests/test_prompt_composer.py::test_craft_carries_no_measurement_from_another_market`
не даёт им вернуться.

Размеры, перемерены 04.08.2026: CRAFT — **6 643** символа, слитый контракт —
`free_contract('id')` = **11 780**, `free_contract('en')` = **10 971**. Минус 44%, и вычтено
ровно то, что было измерено в Джакарте. Это не значит, что промт филиала стал вдвое короче:
контракт — малая доля префикса, остальное база знаний филиала.

## Библиотека

`prompt_library_item` — версионные, branch-agnostic записи трёх видов:

- `persona` — кто продавец (markdown);
- `method` — как продавать на этом рынке: лестница возражений, «дорого», порядок вопросов,
  тон (markdown);
- `catalogue` — набор карточек продуктов (`body` = JSON-список `{slug,title,content,kind,sort_order}`).

Персона и каталог — **разные** записи, а не один комплект: филиал берёт персону у одного
автора, метод у другого, а каталог у него свой. Именно склейка была причиной того, что
индонезийская персона путешествовала вместе с индонезийским прайсом.

**Клон — это копия.** `clone_into_branch` пишет обычные строки `knowledge_doc` / `product`
филиала. Дальше филиал правит их в своём редакторе базы знаний; библиотека в живой промт не
дотягивается, правки филиала в библиотеку не утекают. Провенанс лежит в
`branch_prompt_source` (branch_id, layer, slug, version, когда).

```
docker exec stepan2-api python -m scripts.clone_prompt_library --list
docker exec stepan2-api python -m scripts.clone_prompt_library --sources
docker exec stepan2-api python -m scripts.clone_prompt_library 7 \
    --persona neutral_consultant --method consultative_chat_sales \
    --catalogue starter_catalogue --replace
```

`--replace` выводит текущие строки этого слоя ИЗ ПРОМТА (`in_prompt=false` для документов,
`is_active=false` для продуктов) — ничего не удаляется, откат = вернуть флаг.
`--overwrite` нужен, чтобы переклонировать поверх слага, который филиал уже правил.
`--sources` печатает каждый филиал: pipeline + что он клонировал и какой версии — это и есть
ответ на «кто ещё сидит на методе 1.0».

**Клонирование атомарно.** Конфликт (филиал уже держит такой слаг) обнаруживается ДО первой
записи, и падение любого слоя откатывает всю команду целиком: не бывает состояния «старую
персону сняли, новую не поставили». Без `--version` берётся только `published` — снятая с
публикации запись не заезжает в живой промт по умолчанию; нужна именно она — назовите версию.

## Две сборки промта: `prompt_pipeline`

Настройка филиала, выпадающий список в панели («Промт»). По умолчанию `legacy`.

- **legacy** — `KnowledgeService.full_knowledge_context` (жёсткий список слагов) + слитый
  контракт из `free_mode.py`. На нём остаётся **филиал 1** (37k живых сообщений, закреплённый
  фингерпринт `a63a2a39f44e5339` / 105 846 символов) и филиал 8 (sim-прокси филиала 1 —
  должен собираться так же). Их миграция — отдельный шаг.
- **composer** — `promptlib.composer.compose_context` (ВСЕ документы филиала с флагом
  `in_prompt`) + CRAFT.

Переключение читается в `promptlib.pipeline`; неизвестное значение читается как `legacy` —
опечатка оператора не должна молча подменить промт живому филиалу.

## Что чинит composer

`knowledge.service` грузил документы по кортежу слагов
(`facts_policy`, `facts_market`, `payment_policy`, `policy_prohibitions`,
`objection_playbook`, персона). Документ с другим именем модель не видела **никогда**.
Филиал 7 держал 8 документов и ~35 000 символов своего материала под именами, которых в
кортеже нет: его промт — 16 810 символов против 105 846 у филиала 1.

Теперь выбор — данные: `knowledge_doc.in_prompt` (по умолчанию `true`). Добавил документ —
модель его читает.

**Только на composer.** Жёсткий кортеж `_ALWAYS_DOC_SLUGS` жив в
`app/modules/knowledge/service.py` и после этой миграции обслуживает филиалы 1, 8, 9 и 10 —
то есть весь боевой трафик. От него уходит пока один филиал 7. Список закрывается не этим
шагом, а переводом остальных филиалов; до тех пор `in_prompt` для них ничего не значит.

## Бюджет и порядок блоков

Порядок сборки: персона → факты → метод → каталог. Это же порядок приоритета: при
превышении `free_context_char_budget` (104 000) блоки выбрасываются С ХВОСТА целиком и
пишутся в лог по именам. Хвост — каталог намеренно: потеря одной карточки стоит лидов по
одному курсу, потеря `facts_policy` — всех лидов сразу.

Внутри каталога порядок — `sort_order` филиала, slug только как тай-брейк. Раз каталог и
есть хвост, `sort_order` — это рычаг оператора: какая карточка выпадет первой. (На legacy
карточки по-прежнему сортируются по slug — филиал 1 не двигается.)

Миграция `plib000001` переводит на composer только те филиалы, которых старый список резал
**и** чей материал влезает в бюджет. Бюджет считается по СОБРАННОМУ размеру, а не по сырым
полям: у каждого блока есть заголовок (`[persona x lang=id]`) и `\n\n` между блоками, и на
сотне мелких документов эта разница — тысячи символов. На 04.08.2026 проходит ровно филиал 7
(36 992 символа контента). Филиалы 9 и 10 (Малайзия, Филиппины) режутся тем же списком, но
их 97 645 + ~65 800 символов в 104 000 не помещаются — переключать их вслепую значит
обменять одну тихую потерю на бо́льшую. Сначала оператор снимает `in_prompt` с плейбуков,
которыми филиал не пользуется, потом переключает дропдаун.

## Второй набор библиотечных записей: филиал сайта

`app/modules/website/library.py` держит персону, метод и каталог **чата на лендинге** —
отдельным кортежем `WEBSITE_ITEMS`, не внутри `SEED_ITEMS`. Причина механическая: миграция
`plib000001` клонирует в филиал 7 каждый элемент `SEED_ITEMS`, так что дописать туда — значит
выдать TEST-филиалу вторую персону и второй метод при повторном прогоне. `ensure_library`
поэтому принимает набор параметром.

До S6 тот же текст жил тремя копиями: константа `_SYSTEM` в роуте демо, `SEED_PERSONAS`
в библиотеке персон и — дословно, пятью разделами — продающий контракт филиала. Подробности
и что с ними стало: [website-branch.md](website-branch.md).

## Чего пока нет

Переключателя `in_prompt` в UI базы знаний. Флаг ставится клон-скриптом или SQL; отдельный
проход по `_ui_kb` + i18n — своя задача.
