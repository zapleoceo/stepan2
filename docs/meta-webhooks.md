# Вебхуки Meta — первичный приём для официальных коннекторов

Шаг S8 ветки `feat/connector-architecture`. Филиала 1 (instagrapi, неофициальный API)
не касается вообще: у него нет и не может быть вебхуков.

## Что было сломано

Три вещи, каждая достаточная, чтобы вебхук не работал:

1. `POST /webhooks/meta/{branch_id}` проверял подпись и **выбрасывал тело**, отдавая
   `{"accepted": N}` по числу `entry[]`. Его собственный докстринг утверждал, что «ingest
   is enqueued downstream» — не было ничего. Весь приём шёл опросом.
2. Никто и никогда не вызывал `/{page-id}/subscribed_apps`. Страница не подписана на поле
   `messages` — даже безупречный обработчик не получил бы ни одного сообщения.
3. Вебхук и опрос по-разному называют один и тот же разговор (см. ниже). Наивная запись
   дала бы **два треда** на одного лида.

## Как устроено сейчас

```
Meta ──POST──▶ app/api/webhooks.py       подпись → parse → enqueue → 200 (миллисекунды)
                      │
                      ▼ ARQ job "ingest_meta_webhook"
               app/worker/main.py
                      │
                      ▼
               app/modules/meta/webhook_ingest.py
                      │  page_id → канал филиала (scoped by branch_id!)
                      │  PSID    → external_thread_id  (webhook_threads.py)
                      ▼
               IngestService  ← сюда же приходит опрос
```

- **Ack быстрый.** Meta агрессивно ретраит и отключает медленный эндпоинт, поэтому в
  запросе нет ни БД, ни Graph, ни модели: разбор тела и постановка в очередь.
- **Очередь — не тишина.** Если Redis недоступен, отдаём **503**, а не 200: 200 закончил
  бы ретраи Meta для сообщения, которого у нас нет. `job_id = metahook:{branch}:{first mid}`
  схлопывает только ту повторную доставку, которая пришла, пока первая джоба **в полёте**:
  `WorkerSettings.keep_result = 0` освобождает id сразу после её конца, так что ретрай через
  минуту реально ставится в очередь заново. Безвредным его делает дедуп в `IngestService`,
  а не этот id — id экономит работу, а не гарантирует однократность.
- **Опрос остаётся включённым** как медленная сверка: вебхук, который Meta не доставила,
  всё равно подберётся. Каденс опроса в этом шаге **не меняется** — см. «Дальше».
- **Подпись не идентифицирует тенанта.** `app_secret_for` падает на общий продуктовый
  секрет, поэтому валидная подпись доказывает лишь «у отправителя есть *какой-то* секрет
  приложения», а не «он владелец филиала из URL». Границей тенанта служит поиск канала со
  scope по `branch_id` (`webhook_ingest._channel_for_entry`) — ослаблять его нельзя.

## Согласование идентификаторов (самое важное)

| | ключ треда | нативный id сообщения |
|---|---|---|
| опрос `/{page-id}/conversations` | `conversation.id` (`t_1525755309007110`) | добавляет шаг S3 |
| вебхук `entry[].messaging[]` | нет вовсе, только PSID/IGSID отправителя | `message.mid` |

Вебхук переводится **в ключ опроса**, никогда наоборот — опрос обязан продолжать работать
нетронутым. Два слоя, в порядке дешевизны:

1. **БД.** `IngestService` штампует `Lead.ig_user_id` id отправителя, поэтому для лида, у
   которого тред уже есть, ответ берётся join'ом и не стоит ни одного вызова Graph
   (Meta душит страницу целиком — это не мелочь).
2. **Graph.** `/{page-id}/conversations?user_id={PSID}` — документированный обратный
   поиск, пробуются обе платформы (Messenger, затем Instagram).

Если разговор установить не удалось — сообщение **пропускается**, а не пишется под сырым
PSID. Придуманный ключ и есть тот самый баг с двойным тредом; опрос дотянется до этого
разговора на следующем проходе, так что цена — задержка, не потеря.

### `entry.id` — это ДВА разных id

| `payload.object` | что лежит в `entry.id` | совпадает с `Channel.account_id`? |
|---|---|---|
| `page` | id страницы Facebook | да, его пишет `_routes_connect._persist` |
| `instagram` | id профессионального аккаунта Instagram | **нет**, мы его нигде не храним |

Прямое сравнение с `account_id` для `object='instagram'` не срабатывает **никогда**, то есть
без обходного пути терялись бы все DM из Instagram — основной денежный канал Степана.
Поэтому `_channel_for_entry` для `object='instagram'` и только для него откатывается на
«единственный активный `meta_business`-канал филиала»: один кандидат — однозначная связь,
ноль или больше одного — отказ (лучше цикл опроса, чем DM в чужой инбокс). Для
`object='page'` несовпадение остаётся жёстким дропом: это признак того, что подключили
другую страницу.

Чего этот откат **не** делает: он вообще не смотрит на `entry.id`. Любой `entry.id` при
`object='instagram'` уедет в этот единственный канал — то есть DM с переподключённого или
чужого IG-аккаунта будет принят, а не отброшен. Скоуп по `branch_id` при этом сохраняется, так
что между филиалами это не протекает; риск — «не тот аккаунт» внутри одного филиала.

Настоящее решение — сохранять IG-id при подключении
(`/{page-id}?fields=instagram_business_account`), нужна колонка в `channel`; записано в
`docs/tech-debt.md`.

**Дроп пишется в лог на WARNING** (`META WEBHOOK DROPPED`), а не на INFO. HTTP-слой уже
ответил `200 {"accepted": N}`, Meta ретраить не будет, а лиды продолжают идти опросом — то
есть оператор видит трафик и делает вывод, что вебхуки работают. Тихая потеря на первичном
пути и есть тот отказ, ради устранения которого весь шаг и делался.

### Дедуп — что работает СЕГОДНЯ, а что нет

По нативному id (`Message.external_id = mid`) — **пока нет**: опрос начнёт отдавать тот же
`mid` только после шага S3. До его слияния всё держится на двух эвристиках:

1. **Одинаковый текст в ту же секунду** — `IngestService.duplicate_by_content` (±2 с). Ради
   неё вебхучный timestamp (мс) обрезается до целых секунд, как `created_time` у Graph, и
   ради неё же парсер **не делает `.strip()`**: опрос кладёт текст Graph байт в байт, и
   одного `"\n"` в конце хватало, чтобы сообщение лида сохранилось дважды.
2. **Вложение (фото/шер) — схлопывается в ОБОИХ порядках.** Фото вебхук описывает как
   `🖼 media` + `MediaAsset`, шер — как `🔗 …` + `link_url`, а Graph отдаёт то же сообщение с
   пустым `message` и без вложения. Сравнение текстов их не сопоставит по определению, поэтому
   сравнивается момент времени (±2 с) — единственное, что у двух описаний общее:
   - пустая копия пришла второй → отбрасывается (`MessageRepo.attachment_inbound_at`);
   - богатая копия пришла второй → **дописывается в уже сохранённую пустую строку**
     (`MessageRepo.contentless_inbound_at` + `IngestService._fill_in_blank`), вместе с `mid` в
     `external_id`, чтобы повторная доставка от Meta узналась по id.

   Второй порядок — не экзотика: опрос идёт раз в 2 минуты, а задание вебхука стоит в очереди
   за тем, что arq-воркер уже выполняет. Без этого **каждый** медиа-DM в окне отставания
   сохранялся дважды, вторая строка пустая: она заново открывала 24-часовое окно, сбрасывала
   цикл фоллоу-апов и приходила в контекст модели как молчание.

   **Граница, намеренная.** Совпадения по времени мало: соседняя строка обязана сама нести
   вложение (`MediaAsset` или `link_url`). Иначе обычная текстовая строка съедала бы **другое,
   настоящее** фото, которое опрос принёс секундой позже — тихая потеря на общем пути записи.
   По той же причине `duplicate_by_content` больше не сравнивает пустые тексты: пустота — это
   не содержимое, которое две строки могут разделить, и два вложения подряд схлопывались в одно.

   Что сюда НЕ попадает: `whatsapp.py` никогда не ставит ни `media_url`, ни `link_url`, поэтому
   ни одно его сообщение не может ни сработать как «соседняя строка с вложением», ни попасть в
   ветку дозаписи.

## Подписка страницы

`app/modules/meta/subscribe.py` → `POST /{page-id}/subscribed_apps` из
`_routes_connect._persist`, поля из `STEPAN2_META_WEBHOOK_FIELDS`
(по умолчанию `messages,messaging_referrals`).

`message_echoes` намеренно **не** подписан: наши отправки уже записаны `OutboxSender` в
момент отправки, а эхо приходит с другим `mid` — дедуп по id его не узнает и ответ
задвоился бы в треде и в контексте модели. Эхо отбрасывается и в парсере тоже.

Отказ подписки **не ломает** подключение: пока приложение не прошло App Review на
`pages_messaging`, Meta отвечает 403, и падать на этом — значит блокировать то самое
ревью, которое снимет ограничение. Но провал пишется в лог на ERROR словами самого Graph
(`META WEBHOOK SUBSCRIPTION FAILED`) — «думаем, что вебхуки живые, а они не живые»
это ровно тот тихий отказ, ради которого строка и существует.

## Ответ лиду

Вебхук только **принимает**. Ответ по-прежнему генерирует крон `reply_pending`
(раз в минуту, `second=45`): у него килл-свитч, гард брокера, per-lead гейты и капы
батча — ничего из этого не следует переизобретать на входящем пути.

## Известные ограничения

- **Несколько вложений в одном сообщении** — попадает только первое. Строка `Message` ключуется
  на `mid`, а Meta даёт всей пачке один `mid`, поэтому второй строке понадобился бы
  синтетический id, который опрос воспроизвести не может — ровно тот дубликат, который здесь
  убирается. Остальные пишутся в лог на WARNING, а не проглатываются молча.
- **Сообщение без пригодного `timestamp`** пропускается. `as_naive_utc(None)` — это
  1970-01-01, а такая строка утаскивает за собой `thread.last_in_at` и навсегда выводит тред
  за окно `reply_pending` (`last_in_at > cutoff`): лида просто никогда не ответят.

## Дальше (не в этом шаге)

- **Снизить каденс опроса** для официальных коннекторов, когда подписка подтверждена и
  вебхуки реально идут. Сейчас опрос ходит с прежней частотой; это сознательно —
  выключать сверку до того, как доставка доказана на живом трафике, нельзя.
- **Мгновенный ответ** после вебхучного ingest (вместо ожидания тика `reply_pending`) —
  только вместе с переносом гейтов reply_pending на общий путь.
- `messaging_postbacks` / реакции, если появится сценарий, которому они нужны.
