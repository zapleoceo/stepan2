# Ендпоінт Степана для inbound-колбеку sender

Готово до тестування. Приймає, автентифікує, дедуплікує і записує вхідні повідомлення.
Відповідати лідові поки не вміє — для цього потрібен доступ до MCP sender і мапінг ваших
`project_id` / `branch_id` на наші філії (питання нижче).

---

## Куди слати

```
POST https://stepan2.zapleo.com/api/v1/sender/inbound-callback
Content-Type: application/x-www-form-urlencoded
```

Поля — рівно ті, що в узгодженому контракті: `id`, `external_id`, `from`, `message`, `chanel`,
`project_id`, `branch_id`, `conversation_id`, `chat_id`, і опційні `from_name`, `user_id`,
`attachment`. Решту полів `SendMessage` ми ігноруємо — можна слати всю модель, зайве відсіється.

Реєстрація у вас:

```json
{
  "in": {
    "callbacks": [
      {
        "type": "url",
        "channel": "stepan-bot",
        "url": "https://stepan2.zapleo.com/api/v1/sender/inbound-callback"
      }
    ]
  }
}
```

## Автентифікація

**Зараз, на час інтеграції, ендпоінт відкритий — шліть без жодних заголовків.** Нічого
налаштовувати не треба, просто зареєструйте колбек і надішліть тестове повідомлення.

Це свідомо тимчасовий режим, і він безпечний саме зараз: ендпоінт **лише записує**. Підроблений
запит нікому не відповість, до жодного клієнта не дійде і нічого не витратить. Щойно Степан
почне відповідати лідам — режим вимикається, бо тоді підробка означала б повідомлення
справжньому клієнту від імені бізнесу.

Тож автентифікацію треба узгодити **до відповідей**, не пізніше. Три варіанти, вибирайте
зручний:

**1. Підпис (те, чого хочемо в підсумку).** Заголовок над тілом запиту:

```
X-Sender-Signature: sha256=<hmac_sha256(secret, raw_body)>
```

`raw_body` — байти, які ви реально відправили, до розбору. Порівнюємо за сталий час.

**2. Bearer-токен**, якщо рахувати HMAC незручно:

```
Authorization: Bearer <secret>
```

**3. Список адрес** — **без жодних змін у вашому коді**. Ваш `UrlCallback` шле голе тіло без
заголовків, тож найпростіший шлях: дайте адреси, з яких ходить sender, ми їх впишемо, і
відкритий режим можна вимикати одразу — без секретів і без доробок з вашого боку.

> **Секрет ми надішлемо окремо** — не цим файлом і не цим каналом. Документ лишається в історії
> листування назавжди, у обох сторін; секрет, який там полежав, вважається розкритим. Напишіть,
> як зручно передати (голосом, менеджером паролів, окремим захищеним каналом), або просто дайте
> список адрес — тоді секрет узагалі не потрібен.

## Що ендпоінт відповідає

| Ситуація | Код | Чому так |
|---|---|---|
| Прийнято | `200` | порожнє тіло |
| Дубль за `external_id` | `200` | не `4xx` навмисно: інакше ваші ретраї воюють з нашими |
| Без `external_id` | `200` | приймаємо і помічаємо — відмова означала б втрачене повідомлення |
| Не автентифіковано | `403` | у відкритому режимі не трапляється |

Дедуплікація працює і у відкритому режимі — вона не залежить від того, як ви автентифікувались.

Відповідає одразу, обробка асинхронна — у ваш `connect_timeout = 5s` вкладаємось із запасом.

Дедуплікація за `external_id`: повторний колбек з тим самим id ігнорується. Відповісти лідові
двічі — те, що бачить клієнт, тому це головне, від чого захищаємось.

## Як перевірити, що дійшло

Напишіть нам — ми бачимо кожне прийняте повідомлення в логах і тримаємо останні 50 payload'ів
для звірки. Скажіть час і `external_id`, і ми підтвердимо, що саме отримали.

Це, до речі, головна причина підняти ендпоінт до відповідей на всі питання: нам треба побачити
**реальний формат ваших даних**, передусім телефон у полі `from`. Ті самі ліди пишуть нам і в
Instagram, а ліди в нас зшиваються за номером — якщо формати розійдуться, одна людина стане
двома, і Степан говоритиме з нею двома голосами.

## Що потрібно від вас, щоб рухатись далі

**Блокери відповіді лідові:**

1. **Доступ до MCP sender** — URL і токен. Зручно у вигляді `https://host/mcp/sender?token=...`:
   наш код уже вміє виносити токен з URL у заголовок `Authorization`, як зроблено для MCP CRM.
2. **Перелік інструментів зі схемами** — `sender_reply`, `sender_conversation_send`. Головне:
   **що повертається при помилці**. Нам критично відрізняти «не доставлено клієнту» (ескалюємо
   на менеджера) від «сервер недоступний» (повторюємо).
3. **Мапінг `project_id` → alias** (`crm` / `logbook` / `sintegrum` / `maps`) і
   **`branch_id` → наша філія**. Поки що очікуємо один рядок — Джакарта. Помилка тут означає
   відповідь із каталогу чужої філії.

**Що варто вирішити, поки не пізно:**

4. **Ретраї.** Зараз помилка колбеку лише логується. Якщо наш сервіс у цю мить перезапускається
   (деплой ≈ 2 хвилини), повідомлення ліда **зникає безслідно** — у вас воно є, до нас не
   дійшло, дізнатися нема як. Достатньо трьох спроб з відступом, або методу «віддай inbound з
   такого часу», щоб ми звірялись.

5. **Розмежування з менеджерами.** З лідом у CRM може вже спілкуватись жива людина. Степан
   відповідає завжди, чи лише коли менеджер мовчить N хвилин? І як ми взагалі дізнаємось, що
   менеджер відповів — зараз нам приходять **тільки вхідні**, тож Степан заговорить після
   людини, другим голосом у тому самому чаті. Чи можна підписатись і на `out`, хоча б «для
   відома»?

6. **Тестовий контур** — проєкт/філія або номер, на якому ганяємо інтеграцію, не чіпаючи живих
   лідів. У нас для цього є окрема філія-пісочниця.

7. **Ліміти**: скільки повідомлень на хвилину можна слати без ризику для номера, чи діє
   24-годинне вікно WhatsApp Business і що повертає sender при спробі написати поза ним.
