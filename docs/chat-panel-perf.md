# Открытие панелей: что грузится и почему быстро

`GET /ui/chat/{thread_id}` (`_build_chat_panel` в
[`_routes_chat.py`](../app/api/_routes_chat.py)) рендерит панель чата пятью запросами к
Postgres (шапка лида, сообщения, pending-очередь, события/лог, активные продукты филиала) —
без обращения к брокеру и без N+1.

## Перевод "потребностей" (needs) — кеш + фоновая загрузка

Шапка чата показывает захваченный VPC-профиль лида (`jobs/pains/gains`, см.
[free-mode.md](free-mode.md)), переведённый на язык интерфейса менеджера.
Раньше перевод шёл **синхронно внутри рендера страницы** — первое открытие треда с
непереведённой фразой ждало живой вызов брокера прямо в GET-запросе.

Теперь рендер панели зовёт [`cached_needs`](../app/modules/conversation/needs_translate.py) —
чистую функцию без I/O, которая читает только уже закэшированное в `lead.needs_tr` и
возвращает `(profile, pending)`. Если `pending=True` (есть непереведённая фраза), блок
needs рендерится сразу с фолбэком на оригинальный текст и несёт
`hx-get="/ui/chat/{tid}/needs" hx-trigger="load"` — браузер сам догружает реальный перевод
после того, как страница уже отрисована. Обработчик `chat_needs_lazy` (там же,
`_routes_chat.py`) — единственное место, которое теперь зовёт брокер
(`translated_needs`) и пишет `lead.needs_tr`.

`_needs_for` (тоже в `_routes_chat.py`) — старый синхронный путь, оставлен только для этого
lazy-эндпоинта; больше не вызывается из рендера страницы.

## Медиа-превью сообщений — один JOIN вместо 2×N подзапросов

`fetch_messages`/`fetch_messages_since` ([`_query.py`](../app/api/_query.py)) раньше
резолвили превью медиа двумя коррелированными подзапросами **на каждую строку сообщения**
(`media_id`, `media_kind`) — на длинном треде это Postgres выполнял отдельно для каждого
сообщения. Заменено на один `LEFT JOIN` с `ROW_NUMBER() OVER (PARTITION BY message_id ...)`,
считающий "первый media_asset с данными" один раз для всего треда — тот же результат,
но без квадратичного роста стоимости с длиной треда. Работает и на Postgres, и на SQLite
(оконные функции — 3.25+), так что тесты не завязаны на диалект.

## Панель комментариев — перевод переехал в почасовой воркер

`GET /ui/comments/panel` ([`_routes_comments.py`](../app/api/_routes_comments.py)) делает два
быстрых запроса (список комментариев ~0.11 с, конверсия ~0.04 с). Тормозил не SQL, а перевод:
рендер звал брокер по каждой непереведённой строке **до вывода первого пикселя**, поэтому
после ночного сбора страница висела ровно столько, сколько занимали эти вызовы.

Та же схема, что у needs, но без lazy-догрузки: панель читает только кеш
(`_cached_translations` — чистая функция, ноль I/O), а наполняет кеш
[`translate_pending`](../app/modules/comments/translate.py) внутри почасового
`ingest_comments_branch` ([`worker/main.py`](../app/worker/main.py)) — он и так проходит по
всем новым комментариям. Не успевший перевестись комментарий показывается в оригинале.

`OPERATOR_LANGS` в том же модуле — языки интерфейса минус индонезийский (исходный). Воркер
работает до запроса и не знает, на каком языке будет читать оператор, поэтому переводит на
все сразу. Тест `test_every_ui_language_gets_a_copy` сверяет список с `LANGS` из
`app/api/_i18n.py`, чтобы новый язык интерфейса не остался молча без перевода.

## Аватарки Instagram — не дёргаем протухшие ссылки

Ссылки на аватары с `cdninstagram.com` подписаны и имеют срок жизни (`oe=` — unix-время в
hex). После него CDN отвечает 403. Во «Входящих» перечислены все лиды, в основном спящие, у
которых аватарка снята при последнем их сообщении, — поэтому открытие списка давало десятки
403 в консоли и столько же бессмысленных запросов.

Обновить подпись из UI нельзя: она обновляется только при следующем визите лида
(`leads/profiles.py`, `leads/identity.py`). Поэтому `_avatar_expired`
([`_ui_html.py`](../app/api/_ui_html.py)) просто не отдаёт браузеру просроченную ссылку —
рисуется буква-заглушка. Для оператора картинка не меняется (403 и так показывал заглушку),
но запросов и ошибок в консоли больше нет.
